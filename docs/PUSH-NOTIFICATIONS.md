# Notification previews and the 30-second cooldown

New and existing accounts default to **Show message previews**. The sender's name and first 120 Unicode code points of the message appear in the notification, with the Nest name where applicable. Polls, RSVPs and assignments use their title; attachments without text show a short attachment label. Drafts for the phone's Messages app are sent manually and receive replies outside Churp.

**Your corner → Security → Show message previews** controls future alerts on every device. Turning it off keeps generic titles and bodies, without sender names or message text. Device permission, device opt-out and per-Nest mute settings remain separate. The OS's own notification/lock-screen settings still apply.

## Encryption and authorization

For Churp messages, the sending device makes a small signed OpenPGP preview for each recipient, separately encrypted to that account's public key. A hash of the preview packets is included in the existing signed message send request. The server validates the signature and exact preview audiences before accepting the message. It forwards only the recipient's encrypted packet and public signer metadata; no private keys or plaintext Churp message snippets are sent to the push provider.

The same-origin service worker loads the receiving device's existing wrapped identity from IndexedDB, including archived keys where necessary. In parallel it requests `/api/push/message`, an authenticated, no-store endpoint that checks the latest privacy preference, approved device, current membership/history, blocking and youth approval. It returns authorized sender/Nest metadata and, only for approved devices with previews enabled, the original encrypted message and public signing key. No plaintext Churp message body is returned. The worker checks fingerprints, signatures and message context before decrypting a snippet locally.

Missing, damaged or stale compact packets fall back to the original ciphertext. This covers older open sender tabs, edited originals, groups over 500 members (which skip compact packets to preserve the request budget), and push payloads whose compact packet would exceed the conservative 3,500-byte budget. Being read or muted does not revoke permission to preview an already dispatched message; read/mute settings still suppress new dispatches as described below. Legitimate key rotations are verified using the signed identity transition chain, without requiring the receiving phone to open the conversation first.

Private-key loading and the access request share an eight-second budget; transient request failures receive one retry within that budget. With previews enabled and access confirmed, a device unable to decrypt shows the sender/Nest and **New message**. Expired sessions, revoked access, disabled previews or an unavailable access check use the generic notification without names or text. Untrusted identity changes never reveal a message snippet. Self-managed accounts use only their device-held keys; Churp does not obtain or restore those private keys.

`npm run build` bundles `src/push-preview-worker.js` into the ignored generated file `public/push-preview.js`, then Vite copies it with `sw.js` into the production build. Development startup builds the helper too; restart the development server after changing worker helper code. Both worker files use no-store production responses, and registrations request updates without the HTTP cache. The preview recovery change also updates `sw.js` to trigger worker replacement. Reopen Churp after deployment to receive the update; clearing storage or reinstalling is unnecessary and can lose device-held keys. No new Railway variables are needed; existing VAPID configuration is reused.

## Cooldown and unread badges

The first eligible alert sends immediately. A durable account-wide SQLite window prevents another provider dispatch for 30 seconds, across all subscribed devices and all chat types. Messages arriving during the window replace one pending alert with the latest message; that alert becomes eligible at the end of the window and includes the current unread badge total. There is no separate push for every message in the burst.

Pending alerts are encrypted at rest with the existing persistent key vault and survive restarts. Before delivery, Churp rechecks message existence, current membership/history, mute/read status, blocking and youth approval. Pending alerts for messages already read or no longer accessible are dropped. Current privacy settings are reapplied when the alert actually sends. Definitively rejected sends do not consume a window; uncertain network/provider failures retain it to avoid rapid duplicates. Expired subscriptions are removed.

The phone worker also stores its last alert time in IndexedDB. Delayed or repeated deliveries within that device's window replace the same notification-tray item with `silent: true` and `renotify: false`, while refreshing the badge. Every delivered push still calls `showNotification`, as iOS requires visible push handling. Foreground unread counts and chat delivery remain immediate; closed-app badge updates arrive with the first and coalesced alerts. System delivery timing and presentation remain browser/OS controlled.

## Verification

`tests/push-notifications.test.js` covers preview formatting, self-managed recipient encryption without server keys, authenticated privacy preferences, exact preview audiences and signatures, persistent cross-channel coalescing, badge totals, read/mute suppression, failed subscriptions and simultaneous sends. Recovery tests check read races, missing compact packets, device approval, privacy and revoked Nest/private access. Existing worker badge tests still run. `e2e/push-previews.spec.js` delivers real Chromium service-worker pushes through CDP using the receiver's wrapped IndexedDB identity. It checks compact and full-message decryption, edited text, signed key rotation, read races, missing keys, privacy, quiet replacement and preference persistence. Actual iPhone Safari and system notification presentation should also be checked on a device.
