# Churp message privacy and hybrid key management

Messages, replies, and attachments are encrypted and signed on the browser before upload in both modes. Production rejects plaintext message submissions. Churp defaults to service-managed keys for simple sign-in and recovery. This default is **not end-to-end encryption**: Churp can recover a managed participant's key and read content addressed to that participant.

## Everyday use

New accounts and previously unenrolled accounts get Churp-managed keys automatically. Password and Google sign-in use the same message-key flow. Returning and replacement browsers unlock managed keys after normal authentication, without a recovery-key screen. If an existing Nest member has not visited since encryption was introduced, Churp provisions their default managed identity when a joined reader requests the roster; that person does not hold up sending or conversion of earlier history.

Accounts that already had self-managed keys keep them. The upgrade never uploads their private keys to the managed vault or silently resets them. A returning approved device unlocks automatically; a replacement browser still requires recovery or approved-device transfer. If neither remains, Churp cannot unlock that self-managed account.

Public Nests can be discovered by Tree members, but joining is required to read future messages. New members cannot read earlier messages. Leaving and rejoining starts a new history boundary. Admin powers do not override it. Muting controls notifications and does not change recipient membership.

## Optional self-managed keys

Open **Profile → Security → Message privacy → Use self-managed keys**. Save the displayed `CHURP1-…` key outside the browser, then confirm to enable the mode. Until confirmation, the account remains managed. The app generates a fresh identity on the device, encrypts its recovery backup with a random 256-bit personal secret, and encrypts the historical private key to that new identity. Only the public identity, encrypted backups, and signed transition proofs are uploaded. The new readable private key and recovery secret are never sent to Churp.

The old managed entry is removed from the active vault. Historical keys remain inside an encrypted backup readable with the new self-managed key, so existing messages stay accessible on current and recovered devices. Copies of the former managed key may exist in old backups or have been retained earlier: the switch protects future content and cannot establish retroactive secrecy for past managed conversations. Existing devices with the old key must reload and recover/transfer the new identity.

Self-managed users can choose **Profile → Security → Encrypted messaging → Use Churp-managed keys** and explicitly confirm uploading their current private key to the managed vault. Saved earlier keys remain inside its encrypted key archive, which Churp can now also recover. The personal recovery backup is cleared and pending device-transfer requests are invalidated. Earlier messages remain readable after normal sign-in on a fresh browser. This changes who can recover earlier content, so the confirmation states that clearly. Switching back to self-managed keys always generates a fresh identity and recovery secret, keeps the historical key archive for old messages, and removes the active managed-vault entry. The fresh identity protects future messages; earlier copies and keys already entrusted to Churp cannot become retroactively private. Current clients validate chains of signed transitions across repeated switches; stale devices must reload and recover/transfer the current self-managed identity. Key archives support up to 20 historical keys; the UI prevents another rotation when that limit is reached.

For a new self-managed device, sign in, then enter the recovery key or request approval. On an approved device, open **Profile → Security → Encrypted messaging → Approve a device**, enter the request code, then enter its finish code on the new device. Compare codes directly between your devices. A password or Google login alone cannot restore self-managed messages. Lost devices plus a lost recovery key means lost access; there is no support override or start-fresh reset.

Explicit sign-out deletes local keys. Clearing site data or changing domains can also require restoration. Normal session expiration retains local keys. Self-managed users can replace their recovery backup after saving and confirming the new recovery key; this does not revoke devices or rotate their current message identity.

## Automatic Nest shield

There is no Nest encryption setting. The shield appears in Nest rows and the chat header only when the Nest has at least one joined member and **every joined member has a self-managed current identity with no active managed-vault entry**. Muted members count. Tree or Branch admins who have not joined do not count because they are not recipients. Unenrolled members and empty Nests do not qualify.

Joining, leaving, removal, and a member's successful self-managed activation refresh other clients. A managed-key member joining removes the shield automatically. Once every remaining member qualifies, it returns. The shield explicitly describes **new messages**. It never labels the entire historical transcript as newly private.

Every new message stores the sender's signing fingerprint and whether all its recipients were self-managed at send time. The protection bit is included in the signed encrypted message by current clients and checked when decrypting. Earlier managed messages retain their original label; migrated plaintext is never labeled retroactively E2EE. Attachments inherit their message's protection. The active database stores ciphertext in both modes.

## Storage and trust

- OpenPGP.js 6.3.2 supplies Ed25519 signing, X25519 recipient encryption, and authenticated content encryption. Messages are encrypted to the exact joined recipient set. Files use random per-file secrets; their keys, original names, sizes, and ciphertext hashes are inside signed encrypted messages. The API checks recipient packets, signatures, file ownership, and a roster hash including membership incarnation, fingerprint, and custody. A transaction-time recheck rejects stale membership or key settings.
- Managed private keys are wrapped with AES-256-GCM and account/fingerprint-bound associated data. SQLite holds only the wrapped key. Supply `CHURP_KEY_VAULT_SECRET` from a secret manager as 64 random hexadecimal characters, or let Churp create `DATA_DIR/key-vault.key` with owner-only permissions. The latter lives on the persistent Volume, separately from SQLite. A backup of the entire Volume includes both the database and master and must be protected accordingly. Host access remains sufficient to read managed content.
- Never replace or lose the managed master. Churp refuses startup when managed entries exist but the master is missing, malformed, or cannot unlock a saved entry. Preserve the existing file or configured secret across redeploys. Changing from the file fallback to a secret-manager value requires transferring the **same master**, not generating a new one. Master-key rotation tooling is not included.
- Browser IndexedDB stores current and historical private keys together inside a non-extractable WebCrypto AES-GCM wrapper. This is storage handling, not protection against malicious same-origin JavaScript, XSS, modified web hosting, or a compromised device.
- A managed-to-self transition has proofs from both the old and new keys. Public historical keys remain available to verify old signatures. Contacts accept a valid transition chain and reset manual verification for the new code; unexplained changes still block encryption/decryption. Because Churp previously controlled the managed key, compare new self-managed identity codes out of band for independent assurance. Codes are available under **Nest information → Encryption and security codes**. First contact and a recovered browser use trust on first use.
- There is no independently authenticated membership log, forward secrecy, post-compromise security, or independent cryptographic device revocation. A stolen long-term private key can expose captured content addressed to it. Recipients can retain or forward messages. Removing a member protects future recipient encryption, not old copies.
- Names, avatars, membership, times, file sizes, reply relationships, urgency, and traffic remain server-visible. Shared profile/Tree/Branch/Nest images are not encrypted message attachments. Push alerts omit message contents and keys; message search decrypts and filters loaded messages locally.
- The Churp integration and protocol have **not received an independent security audit**. Published OpenPGP.js audits do not audit Churp. Do not advertise default managed messaging as E2EE or the product as Signal-equivalent.

## Earlier plaintext history and backups

The first encryption release snapshots eligible historical readers once. Later joins and server restarts cannot expand that set. Normal message APIs hide plaintext; only eligible approved browsers with signed requests can retrieve it for conversion. The browser converts messages and files for eligible original readers who still have uninterrupted membership. Missing default identities are now managed automatically.

Conversion preserves IDs, displayed authors, time, and threads. A **Converted by** label identifies the converter; it is not a retroactive author signature. The active body is cleared, replaced files are removed when not still used as shared avatars, and a persistent cleanup queue plus SQLite checkpoint/VACUUM/checkpoint handles active storage cleanup. Pending history shows a retry banner. History with no eligible remaining reader stays inaccessible; do not give later joiners old keys to work around it. Conversion is logical cleanup, not forensic erasure of hosted disks.

Old Railway snapshots, exported files, downloaded copies, and `gatherly.sqlite.before-circles.bak` may still contain plaintext or previous managed keys. Churp does not delete operator backups automatically. Review retention after conversion and a verified replacement backup. Back up SQLite and uploads together, plus the managed vault master and deployment secrets securely. Managed history needs the original vault master; self-managed history still needs the account's personal recovery key or approved device.

## Verification

`npm run check` runs the production build and server tests. `npm run test:e2e:encryption` exercises managed sign-in, opt-in, recovery, transfers, changed identities, real ciphertext and files, history conversion, join boundaries, and live shield changes on desktop, iPhone-sized, and Android-sized Chromium. These are emulations, not actual Safari or system-push tests. `tests/container-smoke.mjs` checks HTTPS/proxy handling, the production CSP, encrypted files, and persistent data across container replacement.

Older layout/administration regression tests explicitly use a legacy plaintext test fixture. It requires `testing: true` and is rejected in production; it is not a deployment downgrade flag. OpenPGP source and licenses are listed in [the public notice](../public/legal/openpgp/NOTICE.txt).
